## 📊 Field Details

### `_id`
- **Type:** String
- **Value:** `str(ObjectId())`
- **Purpose:** Unique identifier for UserPreference document
- **Note:** Already correct - using string format for Spring Boot compatibility

### `user_detail_id`
- **Type:** String
- **Value:** User's detail ID
- **Purpose:** Links preference to specific user
- **Note:** Has unique index in MongoDB

### `watched_list`
- **Type:** Array of Strings
- **Value:** List of feed item IDs user has watched
- **Purpose:** Track viewing history
- **Generation:** Randomly selects 0-10 feed items

### `liked_videos` (NEW)
- **Type:** Array of Strings
- **Value:** List of feed item IDs user has liked
- **Purpose:** Track liked content
- **Generation:** Randomly selects subset of watched videos (0 to all watched)

## 🎯 Why This Change?

### Backend Entity Structure

The backend `UserPreference` entity has this structure:

```java
@Document(collection = "user_preference")
public class UserPreference {
    @Id
    private String id;
    
    @Indexed(unique = true)
    private String userDetailId;
    
    private Set<String> watchedList;
    private Set<String> likedVideos;  // ✅ This field was missing in script
    
    // ... other fields
}
```

### MongoTemplate Upsert

The new upsert code initializes `likedVideos`:

```java
if (userPreference == null) {
    update.setOnInsert("likedVideos", new HashSet<String>());
}
```

Having this field in generated data ensures consistency between:
- Data generated by script
- Data created by backend upsert
